Distributed Training II & Reversible Transformers

From ZeRO's storage sharding to the compute-splitting quartet — tensor, sequence, pipeline, context parallelism — and then a different lever entirely: trading activation memory for compute by making the transformer stack mathematically reversible. This report covers the theory, the from-scratch implementation (four reversible update rules, a Dense and an MoE architecture, a custom autograd engine), and the real results from a 50M-token run of each on an NVIDIA H200.

0 · Motivation

Why this session exists at all

Session 12's ZeRO shards the 16 bytes of training state per weight — optimizer moments, gradients, master weights — across GPUs. But every GPU still runs the whole model on its own micro-batch, start to finish. Three things break under that arrangement.

Break 1

Activations never divide

One 8,192-token sequence through a 30B model stores 127.5 GiB of intermediate activations. An H100 holds 74.5 GiB. ZeRO-3 taken to its limit still can't fit one sequence's working memory.

Break 2

ZeRO-3 rebuilds every layer

Each GPU holds only a weight slice at rest and all-gathers the full layer just before use — 3 parameter-sizes of traffic, every step, for every layer.

Break 3

One sequence can't be split by data parallelism

A 131,072-token sequence produces 2,040 GiB of activations. It's a single sample — no number of data-parallel copies helps. Only splitting the sequence itself does.

The distinction that resolves all three: ZeRO divides what is stored. Tensor / Sequence / Pipeline / Context parallelism divide what is computed. They're not competing techniques — they cut completely different dimensions of the same problem, and production runs (DeepSeek-V3: 16-way pipeline, 64-way expert parallelism, ZeRO-1, together) combine all of them at once.

1 · The five axes

What can actually be divided

Forget the acronyms for a moment. A transformer training step has exactly five things you can cut, plus a sixth — sequence parallelism — that rides along with the second.

Training state
weights, gradients, optimizer → ZeRO
Matrix width
split a layer sideways → Tensor Parallel
Layers / depth
split the stack vertically → Pipeline Parallel
Tokens / context
split one long sequence → Context Parallel
Batch
replicate the model → Data Parallel
TP cuts a layer sideways. PP cuts the model vertically by layers.
CP cuts the input sequence by tokens. ZeRO cuts the duplicated training-state memory.

Tensor parallelism (Megatron-LM, 2019) splits the feed-forward and attention matrices across GPUs and needs 4 all-reduces per layer — traffic so frequent it's kept inside one NVLink-connected node. Sequence parallelism rides alongside it, dividing LayerNorm/dropout activations by the same degree since TP leaves those operations replicated in full. Pipeline parallelism instead slices the model by layer, so a sequence flows through GPUs like an assembly line — its cost is the "bubble," the idle time while the pipeline fills and drains, shrunk by more micro-batches or a smarter schedule (1F1B, interleaved, zero-bubble). Context parallelism divides one long sequence's tokens across GPUs and solves attention's cross-GPU dependency via a ring, an all-gather, or an all-to-all regroup by head (Ulysses).

A production layout nests these from most to least communication-hungry: tensor innermost (fastest link, NVLink), then context, then pipeline, then data parallelism spanning nodes over InfiniBand. DeepSeek-V3 trained 671B parameters with zero tensor parallelism at all — its H800 nodes had NVLink only ~3.2× faster than InfiniBand (vs. ~9× on H100), so it leaned entirely on pipeline (DualPipe) and expert parallelism instead.

2 · The other lever

Reversibility: trading compute for memory that doesn't grow with depth

Every technique above divides activations across more GPUs. Reversibility removes most of them instead — on the same GPU.

An ordinary residual block, pℓ = pℓ-1 + f(pℓ-1), can't be inverted — recovering pℓ-1 from pℓ needs f(pℓ-1), which is exactly the quantity being reconstructed. A reversible update sidesteps this by writing the next state as a function of the state two steps back:

pℓ+1 = pℓ-1 + 2h·fℓ(pℓ)  // forward (midpoint)
pℓ-1 = pℓ+1 - 2h·fℓ(pℓ)  // exact inverse — same f, same p^ℓ

The backward pass therefore never needs the forward pass's cached activations — it walks back down the stack, and at every step it recomputes the state it needs from the state it already holds. Only two boundary tensors persist between forward and backward. A 96-layer model and a 4-layer model store the identical amount: this makes activation memory independent of depth, for a paper-reported cost of roughly 30–50% more compute per step (one extra forward evaluation per layer, and a backward pass already costs more than a forward one).

This is a different technique from every parallelism strategy above — it doesn't need a second GPU at all. It also isn't torch.utils.checkpoint: checkpointing still stores each segment's input and reruns the segment forward; a reversible stack stores no per-layer inputs whatsoever and rebuilds them by algebraically inverting the update rule.

3 · Implementation

What we built

The assignment: train a small LLM, add reversibility, find which variant wins, then push that winner to the largest batch size the GPU can hold — run twice, once for a Dense architecture and once for a Mixture-of-Experts architecture, so the comparison covers both axes of the session.

Two ~20M-parameter architectures, same backbone

n_layer=8, n_head=8, n_embd=256, block_size=512, GPT-2 BPE vocabulary (50,257 tokens). Dense uses one feed-forward MLP per block (19,292,672 params). MoE replaces it with a router over 8 small experts (top-2 active) plus one always-on shared expert, DeepSeek-V3/V4-style (19,833,344 params) — sized so the comparison is apples-to-apples.

Four block types, one shared interface

euler is the ordinary non-reversible residual stack — the paper's own name for the standard update, plain autograd, full activation caching. midpoint, leapfrog, and hamiltonian are each a hand-written torch.autograd.Function: forward runs under torch.no_grad() and saves only the boundary state(s); backward recomputes each layer's local graph on demand via torch.autograd.grad and inverts the update to reconstruct the previous state.

Verified against a brute-force reference before trusting it

Each custom Function was checked against a plain-autograd implementation of the identical recursion on a small synthetic stack: forward output, gradient w.r.t. the input, and every layer's parameter gradients had to match to ~1e-8–1e-9. This caught two real bugs — see Findings below — before any GPU time was spent.

Pipeline: compare, pick a winner, then push the limit

For each architecture: train all 4 block types at a fixed batch size of 32 for 50M tokens each → pick the winner by lowest final validation loss → binary-search the largest batch size that fits (floor = 32, the size already known to fit) → retrain the winner at that size. FlashAttention forced via sdpa_kernel, bf16 autocast, fused AdamW, torch.compile on each block's attention/FFN sub-modules (never on the reversible Functions' hand-written backward — that stays in eager mode).

GPU telemetry logged throughout

Every 50 steps: loss, tokens/second, and — via NVML — GPU utilization, memory-controller utilization, power draw, temperature, clocks, plus torch.cuda allocated/reserved/ peak memory. All charted below from the real run logs.

4 · The four update rules

Euler, Midpoint, Leapfrog, Hamiltonian

Three of these are reversible by construction; one is the ordinary baseline included for comparison.

Euler
pℓ+1 = pℓ + fℓ(pℓ)

The ordinary residual transformer. Not reversible — full activation caching, plain autograd. The non-reversible baseline every other variant is measured against.

baseline
Midpoint
pℓ+1 = pℓ-1 + 2h·fℓ(pℓ)

Explicit midpoint integrator. First-order dynamics — describes the "velocity" of the residual stream. Simplest reversible rule; can be sensitive to real positive eigenvalues in f's Jacobian.

reversible
Leapfrog
pℓ+1 = 2pℓ - pℓ-1 + h²·fℓ(pℓ)

A finite-difference discretization of the second-order wave equation p̈ = f(p). Second-order dynamics — describes "acceleration." Better numerical stability for oscillatory dynamics than Midpoint.

reversible
Hamiltonian
qℓ = qℓ-1 + Attn(LN1(pℓ-1))
pℓ = pℓ-1 + MLP(LN2(qℓ))

Two coupled streams — position p and momentum q — mirroring canonical Hamiltonian mechanics. Attention drives momentum; the FFN drives position. Conserves a discrete analogue of total energy.

reversible

Dropout is forced to 0 for all three reversible variants: the backward pass recomputes each layer's forward function to reconstruct its activations, and a random dropout mask would make that reconstruction diverge from what the real forward pass used.

6 · Discussion

Findings

01

Reversibility matched or beat the non-reversible baseline on both architectures

Dense: midpoint (5.0426) edged out euler (5.0508) with leapfrog and hamiltonian close behind. MoE: leapfrog (4.9733) beat euler (5.0034) by a wider margin. In neither case did adding reversibility cost accuracy at equal token budget — consistent with the paper's own finding that reversible dynamics can match or slightly outperform the standard residual stack.

02

MoE reached a lower loss than Dense, at roughly a third of the throughput

MoE's best variant (4.9733) beat Dense's best (5.0426), but Dense trained at ~510K tokens/s against MoE's ~127–149K tokens/s on the same GPU. The routing/gather/scatter overhead in a from-scratch (non-fused) MoE FFN dominates at this small scale — 8 experts of hidden size 128 is not enough matmul work per expert to hide dispatch overhead, so the quality gain comes at a real throughput cost that a production MoE kernel (grouped GEMM, fused routing) would substantially close.

03

The max-batch run converged worse, not better expected, not a bug

Both architectures found the identical max batch size (383) and both saw validation loss rise at that size (Dense: 5.04 → 6.15; MoE: 4.97 → 6.17). The reason is the token budget, not the reversible update: batch 32 ran 3,051 optimizer steps to cover 50M tokens; batch 383 covers the same 50M tokens in only 254 steps. Far fewer weight updates, at a 12× larger batch, under the same fixed learning rate and warmup schedule — a textbook under-training/LR-mismatch result, not evidence that a bigger batch hurts a reversible model specifically. A real large-batch run would pair the bigger batch with a scaled learning rate and/or a longer token budget.

04

Two real autograd bugs, caught before any GPU time was spent

Both were the same class of error: a custom backward's torch.autograd.grad call assumed every parameter it asked about was actually used in that call's graph.

Hamiltonian — shared owner, disjoint sub-graphs

attn_part and mlp_part are bound methods of the same Block instance, so naively collecting mlp_part.__self__.parameters() pulled in attention weights the MLP-half's graph never touches. torch.autograd.grad raised RuntimeError: ... appears to not have been used in the graph.

Midpoint / Leapfrog — MoE's top-k routing leaves experts unused

With MoEFFN, some experts can receive zero tokens in a given batch — their weights legitimately have no gradient path through that layer's call. Same error, different trigger, only surfaced once MoE was added.

Both fixed with allow_unused=True on the relevant torch.autograd.grad calls, filtering None before accumulating — correct behavior, not a workaround: a parameter with no gradient this step is a legitimate zero, not an error.
